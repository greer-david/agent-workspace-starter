# Coordinate with a work repository

## Ownership

This starter owns personal workspace configuration: Herdr, Git Bash, Bash startup files, user agent preferences, HUD/footer, tab titles and layout. An authenticated work repository owns its required tools, plugin selection/version, project hooks, checked-in skills and recommended editor extensions.

If the user supplies a work repository, read this guide before installing overlapping plugins. Keep private instructions, scripts, identifiers and generated setup reports local. Link to the work repo from the user's local setup record; do not copy its contents into this public repository.

## Setup sequence

1. Establish Git for Windows/Git Bash, GitHub CLI and the selected native agent hosts. Discover the correct work GitHub account, verify repository access and complete organization SSO if needed. Use the coworker's own credentials. For multiple accounts, select credentials per operation where possible instead of changing the global default unexpectedly.
2. Inspect an existing clone before updating it. Read its instructions and discover its default development branch using repository metadata; never assume `main` is the onboarding branch. Fetch without altering local work. Clone the default branch if no clone exists. Do not reset, switch a dirty checkout, merge unrelated work, or touch deployment workflows merely to onboard.
   On Windows, watch for these:
   - Native `jq.exe` writes CRLF into Git Bash. If every plugin reports missing or the wrong version, that's the cause; don't reinstall. Install the starter's `~/bin/jq` wrapper (README Tier 1), which fixes it without editing the work repo. VS Code's `code --list-extensions` has the same CRLF problem; report that one.
   - Login checks can match old display text. If one says you're logged out, confirm with the CLI's own status and exit code before logging in again.
   - With several gh accounts, run one command under a specific account with `GH_TOKEN=$(gh auth token --user <login>) gh ...` rather than `gh auth switch`. If the checker says the repo isn't visible, check which account is active first.
3. Read the work repo's `AGENTS.md`, vendor pointers, setup documentation, `check-setup` skill, and the script that skill names. Follow the current versions in the checkout rather than duplicating their requirement list here. Inspect a script before executing it. Run its read-only checks from the work repo root in the actual Git Bash environment used inside Herdr. If the checker requires a missing bootstrap tool, install that tool first under the user's authorization and rerun; a skipped section is not a pass.
4. Inventory FAIL/WARN findings. Apply safe, authorized local fixes in batches and rerun the checker. The user's explicit installation authorization permits supported local installs even if a skill's default workflow normally hands those steps to a human. Still respect admin prompts, managed policy, licenses and choices that actually require the user. Let the user complete login, SSO and identity decisions; never invent identity or ask for tokens/passwords in chat.
5. Resolve shared plugin setup using the work repo's selected plugins and pinned marketplace release for BOTH Claude and Codex. The starter's recorded version is a snapshot, not an instruction to override a newer work pin. Inspect user- and project-level registrations and installed versions. Align supported host registrations with the work pin; if other active projects require a conflicting global version, report the conflict and use supported project isolation where possible rather than silently breaking them. Reuse existing installations that match.
6. Keep the work repo's checked-in skills authoritative. If it includes the Matt Pocock skills it needs, skip the starter's optional global Matt Pocock plugin unless the user wants the additional namespaced skills. Preserve an existing plugin and explain duplication rather than uninstalling it blindly. Keep project Git guards and hook approvals intact; personal tab-title hooks must coexist with them. Prove a project guard runs in BOTH hosts: trigger one harmless guarded command in Claude and in Codex. Native Codex may not find Git Bash for a hook that calls bare `bash`; `verify.sh` reports which `bash` Windows finds. Review hooks and let each host establish trust normally.
7. Finish this starter's personal workspace configuration. Keep the GUI-launched app and hooks independent of interactive-only Bash aliases. Native Windows tools used by the repo must resolve in the Herdr Git Bash pane as well as any host-specific subprocess environment. Where Python imports are required, verify the actual interpreter used by the plugin/script instead of assuming `python`, `python3` and `py` are interchangeable.
8. Run the work checker again after workspace configuration and complete its manual checklist. Then run this starter's Herdr/layout checks. Keep these as two separate results: the repo checker does not prove the HUD, shell preference or layout works, and a working UI does not prove project tools/auth are ready. Reload/restart each agent as its documentation requires after plugin changes, preserving user sessions where possible.

## Completion

Account for every FAIL/WARN as fixed, explicitly deferred by the user, or blocked with the precise required action. Include checks that were skipped and reasons. Do not claim full setup when interactive authentication or manual checks remain unverified. Save the report locally, with config backups and outstanding login/restart steps; do not commit it to either repository. No cloud refresh, deployment, permission change or production operation is necessary for workstation onboarding.
